# Project description: App for event and task organisation

*As of: 15 October 2026 — foundational document for further prompts
(specification, product design, architecture)*

## 1. Background

The preceding tool research in this project showed: there is no existing tool
that covers governance, task organisation, finances, guest/travel planning, and
communication for self-organised groups in one place. Instead of combining
existing building blocks (Nextcloud, Loomio, Engelsystem, Open Collective …), a
dedicated app is now to be developed — initially with a reduced, clearly
delimited feature set.

## 3. How the team works today

### Distributing tasks

A mix of three ways:

- **Self sign-up** (list, form) — always followed by direct asking.
- **Direct asking** by the core team (message, call) — happens constantly, but
  is itself organising work that should be handed off.
- **Volunteering in a meeting** — first requires gathering people who co-organise,
  partly by direct asking.

### Responsibility within the core team

There are semi-leads per area. Responsibilities are assigned but loose;
informal agreements and tasks changing hands are everyday practice. When a task
changes hands, usually nobody notices — and usually it still works. It only
becomes a problem when a handoff silently fails. **Observe, don't formalise.**

### Keeping the team in sync

- Meetings: every few months at first, later every 4 weeks, once more shortly
  before the festival.
- In between: WhatsApp groups and direct chats.

### Tools in use

Notes:

- **Obsidian** — one core-team member's personal organisation
- **Apple Notes** — shared between two core-team members
- **Notion** — shared with all helpers

Files:

- **iCloud** — personal archive
- **Google Drive** — shared files

### The tool dispute

Seen in at least two groups, both within the core team:

| Camp | Wants | Because |
|---|---|---|
| **Analogue** | to stay dynamic, not maintain tools | tools are too complicated and hard to keep current |
| **Digital** | organised, tool-supported | tools give overview and act as a memory aid |

**Requirement:** simple tools with big impact, acceptable to everyone. Kept
deliberately simple so no overcomplicated structures emerge that hardly anyone
understands.

## 4. Roles

- **Core team** — creates and distributes tasks, sees everything. Some members
  are **semi-leads** for an area; that is a responsibility, not a separate role
  in the app.
- **Helper** — sees and works on only the tasks they are involved in.

Details per feature live in the feature documents (e.g.
[tasks.md](./tasks.md), "Who sees and edits what").

## 6. Principles

### Simplicity guardrail

- A minimal feature list, especially at the start. It may grow where needed,
  but with clear boundaries.
- Clear functions over more text: free text often makes things less clear,
  whereas clear functions are clearly delimited.
- Functions may be visible or editable only for a limited group of people.

**A function is only added when it:**

1. replaces a recurring workaround observed at a real festival,
2. requires helpers to learn nothing new, and
3. can be distinguished from existing functions in one sentence.
